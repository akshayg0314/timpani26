## 요약 (Korean Summary)

- **목적**: TIMPANI에 Event-Driven(L2, Sporadic) 워크로드 지원을 추가하기 위한 상위 요구사항을 정의한다. 먼저 OS·미들웨어와 무관한 **공통 Event/Job 모델**(§2)을 정의한다. 모델은 Event 식별 `(gen, seq)`, **한 Event = 한 Job**, 수락·취득·완료·폐기·취소·중단으로 이루어진 생명주기와 결과, 절대 마감 `t_arr + D`, 규칙 R1~R4와 불변식 I1을 포함한다. SOME/IP 등 특정 미들웨어 식별자·의미론은 TIMPANI 코어에 두지 않는다(전송 계층 중립).
- **범위**: Event/Job 개념 모델, 감지(DET), CBS 격리 실행(CBS), 보호·폴트(PRT), 순서(ORD), 정량 타이밍(TIM), 인터페이스(IF), 런타임 갱신(RTU), 관측(OBS), 비기능(NFR) 요구사항과 수용 기준 AC-008-01~19.
- **단계**: Phase 1은 명시적 Event 연결, CBS 실행(TT 없는 CPU 포함), Event 기준 마감 감시(DeadlineMonitor), 최소 폴트 처리, CBS 예산 관리와 Event/Job 관리의 책임 구분, 배정 CPU의 cpuset 허용 확인, 기본 관측과 FCW 샘플 앱 완성에 집중한다. Phase 2는 정밀 수용식·EDF·다중 생산자 게시·큰 payload 등 고급 기능을 다룬다. 각 요구사항에 P1/P1*/P2를 표기했다.
- **구조**: 모델(①) / 연결·관측(②: 명시적 Event 연결은 Event·Job·마감을 제공하는 유일한 경로이고, 커널 실행 관측은 모든 L2 태스크의 실행 구간과 예산을 제공하며 Event를 얻는 수단이 아니다) / 집행(③: BPF의 CBS·CPU·TT 보호, TIMPANI-N의 마감 감시와 결함 보고, TIMPANI-O의 수용 판정)의 3층으로 나눈다.
- **핵심 변경(v5)**: 마감은 Event 도달 시각에서 시작하는 절대 마감이며, 한 Event는 한 Job에 대응한다(Job을 합치거나 나누지 않는다). 마감 실패는 완료를 기다리지 않고 감지한다. 명시적 연결이 없는 L2 태스크는 budget-only 클래스로 구분한다. A-04는 철회하고 A-06은 정확성 전제에서 해제했다(수용 판정 결과의 조건으로 남는다). v5.2에서는 같은 L2 워커의 CBS 예산 관리와 Event/Job 관리의 책임을 구분하며 앱을 재분류하지 않는다.
- **상태**: Draft v5.2. 지연 상한·큐 상수·API/SHM/proto 제안은 후보값이며 합의·측정 또는 Project Leader 승인이 필요하다(§11 OI-18~OI-19). TIM 후보값은 대상 HW 측정 후 확정한다(OI-5). 하위 문서 SRS/DDR/HLD/LLD-008은 본 문서를 기준으로 개정 중이다.

> **문서 범위 및 작성 원칙**
> 본 문서는 TIMPANI의 `008: Event-Driven Workload Support`를 위한 **상위 요구사항 정의서(REQ)**이다. "무엇을, 왜" 보장해야 하는지를 정의하며, "어떻게"는 DDR-008/HLD-008/LLD-008이 다룬다.
>
> **세 가지 설계 원칙**
> 0. **공통 모델 우선(Model-First)**: Event와 Job을 OS·스케줄러·미들웨어와 무관한 **공통 모델**(§2)로 먼저 정의하고, TIMPANI는 그 모델에 대응하도록 설계·구현한다. 구현 수단(커널 wakeup, futex, sched_ext 콜백, 라이브러리 API)은 모델의 사건을 제공·관측·집행하는 수단일 뿐 모델을 정의하지 않는다.
> 1. **전송 계층 중립(Transport-Neutral)**: TIMPANI 코어(TIMPANI-O/N, BPF, 애플리케이션 라이브러리 계약)는 SOME/IP, DDS, CAN 등 **특정 미들웨어·전송 계층의 식별자나 의미론을 포함하지 않는다.** TIMPANI가 아는 것은 공통 모델의 Event source, 앱이 명시적 연결 경로로 제공한 Event 정보(도달 시각, 식별자, payload), 그리고 커널이 관측한 실행 구간뿐이다. 미들웨어 고유 처리(서비스/인스턴스/이벤트 ID, 구독, 역직렬화)는 애플리케이션 또는 앱 측 어댑터의 책임이다.
> 2. **단계적 접근(Phased)**: **Phase 1**은 현실적이고 단순한 기본 기능(명시적 Event 연결, CBS 격리 실행, Event 기준 마감 감시, 최소 폴트 처리, 기본 관측)에 집중하여 `timpani26` 구현과 FCW 샘플 앱 완성을 함께 이끈다. **Phase 2**는 Phase 1 검증 후 고급 기능(EDF 순서, 윈도우 기반 수용 판정, 증분 갱신, 미들웨어 경계 관측, watchdog 등)을 다룬다. 요구사항 ID는 Phase와 무관하게 안정적으로 유지하며, Phase 열로 범위를 표시한다.
>
> **키워드 규약**: **SHALL** = 필수, **SHOULD** = 권장, **MAY** = 선택.
> **단위 규약**: 모든 시간 값은 단위를 명기한다(µs/ms/ns). 정량 요구사항은 백분위수와 관측 구간을 함께 명기한다. 합의되지 않았거나 측정되지 않은 수치는 `(후보)`로 표시하며, 확정 전에는 합부 기준으로 쓰지 않고 "합의된 상한"으로 참조한다.

## 1. 개요 및 문제 정의 (Overview & Problem Statement)

### 1.1 배경
SDV(Software-Defined Vehicle) 환경의 워크로드는 고정 주기로 동작하는 제어 태스크(L1 Periodic)뿐만 아니라, 레이더/라이다 객체 감지, 긴급 제동 트리거, 미들웨어 메시지 수신 등 **외부 이벤트 도달에 의해 비주기적(Sporadic)으로 활성화되는 안전 중요(Safety-Critical) 워크로드(L2)**를 포함한다. 이러한 워크로드는 "언제 실행되는가"가 외부 세계에 의해 결정되므로, TIMPANI는 실행 시각을 미리 정할 수 없고 **(a) Event의 도달 시각을 정확히 기록하고, (b) 도달 이후의 응답 시간을 바운드하며, (c) 예산 초과가 L1 및 다른 L2에 전파되지 않도록 격리**해야 한다.

### 1.2 일반적 Event-Driven 워크로드의 요구 특성 (설계 중립적 정리)
TIMPANI 구현과 무관하게, 안전 중요 Event-Driven 워크로드를 실시간 스케줄러가 지원하려면 다음이 필요하다. 본 문서의 요구사항은 이 목록을 TIMPANI 아키텍처(HSF, sched_ext, TT+CBS)에 투영한 것이다.

| # | 특성 | 설명 | Phase |
|:--|:--|:--|:-:|
| G1 | **Sporadic 태스크 모델** | MIT(최소 도달 간격), WCET, 상대 마감(D)을 선언. D는 **Event 도달 시각** 기준이어야 함(디스패치 시점 기준이 아님) | P1 |
| G2 | **도달(arrival) 기록** | Event가 "언제 도달했는가"를 명시적 연결 경로가 수락 시점에 기록. 커널 관측만으로는 도달 시각을 알 수 없으며, 관측점이 늦을수록 응답 시간 측정이 낙관적으로 왜곡됨 | P1(명시적 연결) / P2(미들웨어 경계) |
| G3 | **Job 경계 정의** | 1회 Event 처리의 시작/끝이 명확해야 응답 시간·마감 판정이 성립. 처리 도중의 내부 블로킹(뮤텍스/I/O)은 새 Job이 아니며, 커널 수면을 Job 경계로 쓰면 안 됨 | P1(워커의 명시적 취득·종료. 연결 없는 태스크에는 Job 경계가 없다, OI-1 종결) |
| G4 | **대역폭 격리** | 예산(C_s)/주기(T_s) 서버로 CPU 사용량을 상한. 이벤트 폭주(MIT 위반)·실행 시간 초과가 타 워크로드에 전파되지 않아야 함(FFI) | P1 |
| G5 | **수용 판정** | 이용률 검사만으로는 D < MIT인 경우의 마감 보장이 불충분. 상위 계층(L1 TT 슬롯)에 의한 최대 블로킹과 동일 CPU 내 타 서버 간섭을 반영한 응답 시간 바운드 필요 | P1(단순식, 블로킹 없는 Job) / P2(윈도우 수요) |
| G6 | **깨움 지연 바운드** | 도달 → 실행 개시 지연을 백분위수로 바운드. 도달 시각 → 실행 가능(t_arr→runnable)과 실행 가능 → 첫 실행을 구분. CPU가 유휴/Gap일 때와 상위 계층이 점유 중일 때를 구분 | P1 |
| G7 | **보충 결정론** | 스로틀된 서버는 보충 시각에 "확실히" 실행 가능 상태로 복귀해야 함. 다른 활동에 기대는 지연 보충은 바운드가 없음 | P1 |
| G8 | **MIT 위반 처리** | MIT보다 빠른 도달을 계수하고, 격리 유지(예산 내 흡수/지연/폐기)와 보고를 분리 | P1 |
| G9 | **동일 CPU 다중 서버 순서** | 여러 Sporadic 서버가 한 CPU를 공유할 때의 우선 순서(FIFO/EDF)가 마감 보장식에 들어가야 함 | P1(FIFO) / P2(EDF) |
| G10 | **이벤트 침묵 감시** | 기대 도달이 없을 때(센서 탈락)를 감지하는 감시(watchdog) 수단 | P2 |
| G11 | **런타임 추가/제거** | Sporadic 워크로드의 추가/제거가 기존 L1/L2 타이밍을 교란하지 않아야 함 | P1(추가/제거 가능) / P2(무교란 보장) |
| G12 | **관측성** | 도달/취득/완료 기록, 실행 구간, 예산 사용량, 위반 카운터를 검증 프레임워크가 수집 가능해야 함 | P1 |
| G13 | **애플리케이션 식별/복원력** | 이벤트 처리 스레드가 늦게 생성되거나 재시작되어도 정책이 재적용되어야 함 | P1(재스캔) / P2(cgroup 메타데이터) |

### 1.3 현재 한계점 및 해결 과제
기존 설계([DDR-001](DDR-001-workload-model.md), [DDR-005](DDR-005-sched-ext-bpf-scheduler.md), [DDR-007](DDR-007-tt-cbs-integrated-scheduling.md))와 `timpani26` 코드베이스는 L2 워크로드에 CBS 예산을 할당·차감하는 메커니즘을 **이미 end-to-end로 갖추고 있다**(TemporalClass → Mechanism::CBS → `CbsConfig` → BPF `cbs_map` → 예산 차감/스로틀). 그러나 **Event-Driven 워크로드의 근본 동작 모델**에 대해 다음이 정의되지 않았거나 구현이 결정론 요구를 만족하지 못한다(근거: §10 갭 요약표).

1. **Event와 Job의 정의 부재**: TIMPANI 관점에서 무엇을 Event 수락과 Event 처리(Job)의 시작·끝으로 볼지 기준이 없다. 현 BPF는 **모든** wakeup에서 `activation_ns`를 덮어쓰므로(`timpani.bpf.c:256`), 처리 도중의 뮤텍스/I/O 블로킹 후 재깨움이 새 활성화로 오인되어 마감 판정과 도달 계수가 오염된다.
2. **마감 기준과 판정 시점의 불일치**: 마감의 기준은 Event 도달 시각이어야 하지만 현 코드는 커널 wakeup 시각에 묶여 있고, L2 마감 판정은 완료 시점이 아니라 매 stopping마다 수행된다.
3. **Event 감지와 CBS 런타임의 연결**: 활성화된 태스크가 L1(TT)과 간섭 없이 CBS 예산 내에서 실행되고 완료 후 재대기하는 종단간 흐름은 존재하나, (a) 보충이 BPF ops 경로 진입에만 의존해 **보충 지연 상한이 없고**, (b) `DSQ_CBS`가 전역 큐라서 L2 태스크가 **배정 CPU 밖에서 실행**될 수 있어 CPU별 Gap 분석(DDR-007)이 무효화되며, (c) 수용 판정이 이용률만 보고 **TT 블로킹·D<MIT·동일 CPU 서버 간섭·tick 초과 간섭**을 반영하지 않는다.
4. **정량 바운드 부재**: 깨움 지연, 보충 지연, 예산 초과 허용치, 마감 감지·보고 지연에 대한 수치 요구사항이 없어 검증 프레임워크가 합부를 판정할 수 없다.
5. **인터페이스 불일치**: Pullpiri→O proto에 MIT 전용 필드가 없고 `period`를 재사용한다. O→N에는 `ExecutionModel.EVENT_DRIVEN`이 선언만 되어 있고 항상 `TIME_TRIGGERED`로 발행된다. BUDGET_EXCEED/WATCHDOG 폴트는 O→Pullpiri 경계에서 UNKNOWN으로 소실된다.
6. **전송 계층 특정 PoC**: `examples/someip/libtimpani_rt`는 SOME/IP의 service/instance/event ID를 API 계약에 포함하고(`timpani_evt_register(wl, task, svc, inst, evt, mit)`), 자체 SHM(`/timpani_rt`)에 MIT·E2E 폴트를 기록하지만 TIMPANI-N은 이를 소비하지 않는다. 서버 키 해시도 BPF와 불일치한다. 이는 원칙 1에 위배되므로 재설계 대상이다(§12).

## 2. 개념 모델: 공통 Event/Job 모델 (Common Event/Job Model)

> 이 절은 **특정 OS·스케줄러·미들웨어·라이브러리와 무관한 공통 모델**을 정의한다. §4의 요구사항, 하위 문서(SRS/DDR/HLD/LLD-008), 애플리케이션 계약, 검증 프레임워크는 모두 이 모델의 용어와 규칙으로 기술된다. 구현 수단(커널 wakeup, futex, sched_ext 콜백, 연결 API)은 §2.7의 **연결·관측 계층**에 속하며 모델을 바꾸지 않는다.

**공통 용어의 정본:** OVERVIEW와 상세 문서 REQ/SRS/DDR/HLD/LLD/P1-008은 아래 용어를 같은 의미로 쓴다. 다른 문서는 이 정의를 참조하며 별도의 번역명이나 앱 분류를 만들지 않는다.

| 용어 | 정의 |
|:--|:--|
| **CBS 예산 관리** | 같은 L2 워커의 서버 윈도우 단위 CPU 예산 집행·예산 보충·스로틀 책임. CPU 고정과 BPF 실행 구간 관측은 이에 연관된 공통 메커니즘이다. Job 시작만으로 예산을 새로 주지 않는다 |
| **Event/Job 관리** | 같은 L2 워커에 대한 Event 수락·거절, 식별·큐 관리, 명시적 Job 생명주기, 도달 기준 MIT 계수와 마감 감시 책임. 명시적 Event 연결은 이 책임에 필요한 정보를 제공하는 수단이다 |
| **도달(arrival)** | 입력 어댑터가 선언한 경계에서 입력을 인지한 사건. 도달 시각과 MIT 계수 대상은 §2.5~§2.6을 따른다. 수락된 도달만 Event가 된다 |
| **수락/거절** | 게시 요청을 Event로 받아들이거나 오류로 돌려주는 결과. 워크로드 배치의 수용 판정과 구분한다 |
| **게시(post) / Event 대기(wait) / 종료(done)** | 어댑터가 Event를 게시한다. 워커는 처리할 Event가 있을 때까지 대기하며, 같은 wait 호출 안에서 Event 한 건의 Job 시작을 확정·기록하고 Event를 인계받아 반환한다. QUEUED Event가 있으면 블로킹 없이 반환한다. done은 워커의 명시적 Job 완료·폐기다. 별도의 공개 취득 API는 없다. TIMPANI의 닫기는 §2.3을 따른다 |
| **Job 시작 상태 전이 (`QUEUED → RUNNING`) / 처리 시작 확정** | wait 내부에서 해당 Event의 처리를 시작한다고 확정하는 논리적 전이. SHM 구현의 CAS(compare-and-swap)는 읽어 둔 상태 워드와 현재 값이 같을 때만 새 값으로 바꾸는 원자적 조건부 갱신이다. 추가 큐·공개 API·스케줄러 연산이 아니며, 데이터 복사와도 구분한다. 이 문서에서 워커의 "취득"은 이 전이를 가리키며 별도 공개 API가 아니다 |
| **예산 보충(replenishment)** | 기존 윈도우 규칙에 따라 서버 예산을 채우는 동작. Event 수락이나 Job 시작 자체와 구분한다 |
| **예산 소진(budget exhaustion)** | 차감 뒤 잔여 예산이 0인 상태. 그 자체로는 스로틀이 아니다(PRT-001) |
| **스로틀(throttling)** | 잔여 예산이 0인 실행 가능 태스크의 추가 실행을 BPF가 막는 것. 소진한 뒤 잠든 태스크는 스로틀되지 않는다 |
| **승격(promotion)** | 예산 보충 뒤 스로틀된 서버를 실행 큐로 옮기는 동작 |
| **수용 판정(admission)** | 배치 대상 CPU의 모든 L2 태스크에 같은 수용식과 기존 전제를 적용하는 사전 스케줄 가능성 판정(CBS-004) |
| **실행 구간(execution interval)** | 커널이 관측하는 실행 가능 전이부터 다음 자발적 수면까지의 단위. Event 도달이나 명시적 Job 경계가 아니다 |

**CBS 예산 관리와 Event/Job 관리는 같은 L2 워커의 상호 보완적 책임이지, 두 앱·클래스·모드나 앱의 두 부분이 아니다.** L2는 Accepted DDR-001의 `Sporadic + SafetyCritical` 분류를 그대로 따른다. 명시적 Event 연결 여부로 L2를 다시 분류하지 않는다. 연결을 쓰지 않아도 기존 CBS 예산 관리·CPU 고정·실행 구간 관측은 유지된다. 다만 Event 도달 시각·Job 기록·MIT 계수·Event 기준 마감 감시에 필요한 기록을 얻지 못하며, BPF 실행 구간에서 이를 추정하지 않는다. 선택적 연결과 기존 호환성의 범위는 바꾸지 않는다(DET-003, IF-001, NFR-003/005).

### 2.1 3층 구조

| 층 | 내용 | 바뀌는 조건 |
|:--|:--|:--|
| **① 모델** | Event source / Event / Job, 생명주기와 결과, 마감 규칙, R1~R4, I1, 타이밍 제약(MIT, D) | 바뀌지 않는다(본 절) |
| **② 연결·관측** | **명시적 Event 연결**: Event 수락, Job 취득·명시적 종료, 결과 기록. Event·Job·마감을 제공하는 유일한 경로다. **커널 실행 관측**: 모든 L2 태스크의 실행 구간과 CBS 예산. Event를 얻는 수단이 아니다 | 연결 방식 추가·교체 시 |
| **③ 집행** | BPF: CBS 예산 집행, CPU 고정, TT 보호, 실행 구간 관측. TIMPANI-N: Event 기준 마감 감시(DeadlineMonitor), 결함 보고, 통계. TIMPANI-O: 수용 판정, 배치 | 정책 변경 시(DDR-008) |

TIMPANI의 기능은 "②가 제공한 ① 사건에 ③을 적용한다"로 정의된다. 명시적 Event 연결은 Event/Job 관리에 필요한 사건과 Event 기준 마감을 제공한다. 연결이 없어도 같은 L2 워커의 CBS 예산 관리·CPU 고정·실행 구간 관측은 유지된다(MOD-011). 새로운 이벤트 전달 수단(DDS, CAN, 파이프라인 선행 태스크 등)은 ②의 연결 방식을 추가하는 것으로 수용하며 ①·③은 그대로다.

### 2.2 엔티티

| 엔티티 | 정의 | 식별·속성 |
|:--|:--|:--|
| **Event source** | L2 태스크에 Event를 공급하는 선언된 발생원. TIMPANI는 발생원의 종류·내용·전송 계층을 알지 못한다. 명시적 연결로 Event를 게시하는 source만 Event를 가진다 | 식별자 `(workload_id, task_id)`, 소비 워커 1개, MIT(연속 도달의 최소 간격). P1: L2 태스크당 1개, 암묵 선언. P2: 태스크당 여러 개, 명시 선언(OI-16) |
| **Event e** | Event source에 **수락된** 1회 도달 | 식별 `(gen, seq)`: `seq`는 source 안의 게시 순번, `gen`은 등록 세대(source가 다시 활성화될 때마다 증가). 속성: 도달 시각 `t_arr`(단조 시계), 절대 마감 `t_dl = t_arr + D`(수락 시 1회 계산, 불변), payload(TIMPANI가 해석하지 않는 바이트) |
| **Job j(e)** | Event e 하나의 처리. 여러 Event를 합치거나 나누지 않는다 | 시작 `t_begin`(워커가 e를 취득한 시각), 끝(워커의 명시적 종료 `t_end` 또는 TIMPANI의 닫기 시각), 결과, 표식 |
| **L2 태스크** | DDR-001의 `Sporadic + SafetyCritical` 분류에 속하며 워커 스레드를 가진 실행 주체. CBS 예산 관리와 Event/Job 관리의 책임 구분은 이 분류를 바꾸지 않는다(MOD-011) | `(workload_id, task_id)`, WCET C, 상대 마감 D, MIT |
| **실행 구간** | 커널이 관측한 워커의 실행 단위: 실행 가능 전이(활성화) → 첫 실행 → 자발적 수면 | `t_act`, `t_start`, `t_sleep`(BPF 관측). **Job 경계가 아니다** |

Event(도달)와 Job(처리)은 서로 다른 개념이다. MIT는 Event 도달에, C와 마감은 Job에 적용된다. 실행 구간은 커널 관측의 단위이며 Job과 1:1일 필요가 없다. 한 Job은 한 실행 구간에 끝날 수도 있고, 블로킹·선점으로 여러 실행 구간에 걸칠 수도 있다.

### 2.3 Event 생명주기와 결과

```text
  게시(post) ──► 수락 거절: E_INACTIVE, E_FULL, E_INVAL → Event가 아님 (E_FULL은 넘침으로 계수)
     │ 수락: (gen, seq), t_arr, t_dl = t_arr + D 고정, 감시 시작
     ▼
  QUEUED ── 워커가 취득 (t_begin) ──► RUNNING ── 워커 완료 (t_end) ──► COMPLETED   (성공 종료)
     │                                  │
     │                                  ├── 워커 정책 폐기 ──────────► DISCARDED   (성공 아님)
     │                                  └── TIMPANI 닫기 (워커 종료, 재등록) ─► ABANDONED
     └── TIMPANI 닫기, Job 시작 전 (비활성, 재등록, 데몬 정리) ─────► CANCELLED
```

- **QUEUED**: 수락되었고 아직 해당 Event의 Job 시작이 확정되지 않았다. 워커가 CPU에서 이전 Job을 처리하는 동안에도 다음 Event는 QUEUED일 수 있다.
- **RUNNING**: wait 내부에서 해당 Event의 Job 시작을 확정했다. 현재 CPU에서 실행 중이라는 뜻이 아니며, 선점·스로틀·블로킹 중에도 종료 상태로 전이할 때까지 유지된다.
- **COMPLETED**: 워커가 처리를 마쳤다고 명시했다. 성공 종료는 이것뿐이다.
- **DISCARDED**: 워커가 정책적으로 Event를 포기했다. 처리 실패가 아니지만 성공도 아니다.
- **CANCELLED**: TIMPANI가 Job 시작 전에 닫았다(source 비활성화, 재등록, 데몬 정리).
- **ABANDONED**: TIMPANI가 실행 중에 닫았다(워커 종료, 같은 source의 재등록).
- 터미널 상태(COMPLETED, DISCARDED, CANCELLED, ABANDONED)는 최종이며 되돌릴 수 없다.
- **거절**: 게시가 거절된 경우 Event는 생기지 않는다. `E_INACTIVE`(source 비활성, 워커 미바인딩, 제거, 데몬 중지), `E_FULL`(큐 가득 참, 넘침으로 계수), `E_INVAL`(인자 오류)이다.
- **REVOKED**: 게시 도중 source가 비활성화되거나 재등록되어 롤백된 내부 상태다. Event가 아니며 수락 수에 들지 않는다.

이 상태들은 공통 Event/Job 모델의 논리적 생명주기이며 SHM Event 레코드에 표현된다. BPF DSQ 소속이나 워커의 현재 CPU 실행 여부와는 별개다. wait의 반환 시 Event 인계는 같은 호출의 결과이지, 별도 공개 API 단계가 아니다.

**Job 시각과 결과**

- 시작: 워커가 Event를 취득한 시각 `t_begin`. 끝: 워커의 명시적 완료·폐기 시각 `t_end`, 또는 TIMPANI가 Job을 닫은 시각.
- TIMPANI가 닫은 Job은 `t_end` 대신 닫은 시각을 가진다. Job 시작 전에 닫힌 경우 `t_begin`이 없다.
- 응답 시간 `R = t_end − t_arr`. Event 기준 마감 충족은 **COMPLETED이고 `t_end ≤ t_dl`**이다.
- 실행 구간의 시각 `t_act`, `t_start`, `t_sleep`은 커널이 관측하며 Job 경계가 아니다(§2.7).

### 2.4 Job 규칙과 불변식

- **Job j(e)**: 수락된 Event e 하나의 처리다. 여러 Event를 합치지 않는다(MOD-009). 워커가 Event를 취득하는 것으로 시작하고, 워커의 명시적 종료 또는 TIMPANI의 닫기로 끝난다(DET-007).
- **R1 (대기 중 도달)**: 워커가 취득을 대기하는 중에 Event가 수락되면 그 Event의 Job은 즉시 취득 가능해진다.
- **R2 (처리 중 도달)**: Job이 실행 중일 때 수락된 Event는 `QUEUED`로 남는다. 실행 중인 Job에 추가되지 않으며 유실되지 않는다.
- **R3 (연속 Job)**: Job이 끝났고 `QUEUED` Event가 있으면 워커는 잠들지 않고 가장 오래된 Event의 Job을 시작한다. 연속된 Job은 서로 다른 Job이다.
- **R4 (소비)**: Job 하나는 정확히 Event 하나를 소비한다. Event는 source 안에서 FIFO 순서로 취득된다.
- **불변식 I1**: 수락된 모든 Event는 정확히 하나의 터미널 상태에 도달하며, Job과 수락된 Event는 1:1로 대응한다.
- **동시 발생 경계**: 두 사건(도달과 완료 등)의 선후는 연결 경로가 게시한 순서로 정한다.
- 정상 조건(MIT 준수, 모든 Job이 `C ≤ D ≤ MIT` 조건에서 마감 충족)에서는 R2·R3이 발생하지 않으며 Job과 Event는 1:1이다. R2·R3의 발생 자체는 MIT 위반 또는 선행 Job의 마감 초과를 뜻하는 관측 지표다.

### 2.5 마감 규칙: 결과와 완료 시각

**절대 마감**: Event의 마감은 `t_dl = t_arr + D`다. 수락 시 1회 정해지며, 활성화·보충·재개·워커 지연에 의해 뒤로 옮기지 않는다. **활성화 시각 + D는 마감으로 쓰지 않는다.** 판정은 감시 시계로 `t > t_dl`(엄격한 초과)을 쓴다.

**마감 실패(MISSED)**: Job은 다음 중 하나이면 마감 실패다.
- 시각 `t > t_dl`에 아직 열려 있다(QUEUED 또는 RUNNING).
- `t_dl`을 지난 뒤에 끝났다. 완료, 폐기, 취소, 중단 모두 해당한다.

**규칙**

- MISSED는 Job당 한 번 설정되는 표식이며 해제되지 않는다. 이후의 종료가 이미 설정된 실패를 지우지 않는다.
- `t_dl` 이하에서 끝난 Job은 실패가 아니며, 그 시점에 마감 감시가 끝난다. 정상 완료뿐 아니라 TIMPANI가 닫은 Job(CANCELLED, ABANDONED)도 마감 전이면 실패가 아니다. 이 닫기는 실패가 아닌 별도 결과로 사유와 함께 계수한다(성공이 아님). 이 해석은 확인 대상이다(OI-21).
- 마감 실패 감지는 완료를 기다리지 않는다. 대기, 실행, 선점, 스로틀, CPU 유휴 상태 모두에서 감지한다(PRT-009).
- 마감 전 워커가 명시적으로 폐기(DISCARDED)한 항목은 성공 완료가 아니지만 실패도 아니다. P1에는 워커가 쓰는 취소 호출이 없다. 마감 이후의 폐기·취소·중단은 실패다.
- 수집이 늦었다는 이유만으로 정시 완료를 실패로 판정하지 않는다. 수집 측은 기록된 완료 시각으로 판정한다.

**완료 시각 `t_end`와 경합 규칙**

- `t_end`는 워커가 완료를 게시하기 직전에 읽은 시각이다.
- Job은 `t_end ≤ t_dl`이고 감시 측이 이미 실패로 표시하지 않았을 때 정시 완료다.
- 감시 측의 표시가 워커의 시각 읽기와 완료 게시 사이에 끼어들면 완료 게시는 실패하고, 워커는 시각을 다시 읽어 재시도한다. 이때 다시 읽은 시각은 `t_dl` 이후이므로, 기록된 `t_end`와 MISSED 표식이 서로 어긋나지 않는다.
- 허용되는 오차: 정시로 기록된 Job이 `t_dl` 직후에 게시될 수 있다(워커가 시각 읽기와 게시 사이에 선점된 경우). 그러나 최초 감시 주기 이후로 늦어지지는 않는다. 이 해석은 확인 대상이다(OI-20).

**P1 한계**: 데몬이 내려간 동안에는 만료된 Event를 감시하는 주체가 없다. 재시작 후 정리에서 발견한 실패는 실시간 보고가 아니라 사후 기록이다(PRT-009).

### 2.6 도달 간격(MIT) 제약

- MIT 제약은 **도달**에 대한 것이다. 같은 source의 연속된 두 도달 사이 간격은 `min_inter_arrival_us` 이상이어야 한다.
- 도달을 계수하는 시도는 모두 도달로 센다. 수락, 큐 가득 참으로 거절, REVOKED 롤백이 여기에 든다. source 비활성으로 첫 검사에서 거절된 게시는 도달이 아니며 아무것도 바꾸지 않는다.
- 위반된 도달도 **수락하여 큐에 넣는다**. 위반은 계수하고 보고한다(PRT-004). 유실하지 않는다.
- 활성화 간격에 의한 근사 계수는 없다. 활성화 간격은 도달 간격이 아니므로 MIT 판정에 쓰지 않는다.
- 위반이 계속되면 큐가 쌓이고 뒤따르는 Job이 마감을 놓칠 수 있다. 이는 막지 않고 보고한다.

### 2.7 연결·관측 계층

| 경로 | 제공하는 것 | 제공하지 않는 것 | Phase |
|:--|:--|:--|:-:|
| **명시적 Event 연결** (앱이 호출) | Event 수락(도달 시각, 식별자, payload 보관), Job 취득과 명시적 종료(결과), Event 기준 마감과 감시 | 앱이 연결하지 않은 Event. 연결 경로를 거치지 않은 도달 | P1 |
| **커널 실행 관측** (모든 L2, 앱 변경 없음) | 실행 구간(실행 가능 전이, 첫 실행, 자발적 수면), CBS 예산 사용과 스로틀, 실행 CPU | Event 도달, Job 경계, Event 기준 마감. 커널 깨움의 원인이 Event인지 구분할 수 없으므로 Event를 얻는 수단이 아니다 | P1 |
| **미들웨어 경계 관측** | 미들웨어 수신 지점에서의 도달 | 미들웨어별 구현 필요 | P2 |
| **선행 태스크 완료** | 파이프라인에서 선행 Job 완료가 후속 source의 도달이 됨 | REQ-DD-001 | P2+ |

- 명시적 Event 연결은 Event 기준 마감의 **유일한** 경로다. 앱은 Event의 도달 시각과 payload를 연결 경로에 게시하고, 워커는 Event를 하나씩 취득하여 Job을 시작하고 명시적으로 끝낸다. 수락·거절·넘침은 연결 경로가 확정하며(IF-007), 앱이 별도의 payload 큐를 유지하지 않는다.
- 커널 실행 관측은 Event를 얻는 수단이 아니다. 실행 구간을 CBS 예산 집행과 실행 기록에 쓴다. 커널 관측만으로 등록된 L2 태스크를 "Event 기준 마감 지원과 동등하다"고 설명하지 않는다.
- 두 경로를 "같은 결과를 내는 두 방법"으로 설명하지 않는다.
- 연결 경로의 API 제안(libttsched 명칭 `ttsched_evt_open`, `ttsched_evt_post`, `ttsched_evt_wait`, `ttsched_evt_done`)은 IF-005와 IF-007의 제안이며 Project Leader 승인이 필요하다.
- 연결 경로는 P1에서 다음 제약을 가진다(IF-005, IF-007, C-08, C-09). 워커 스레드는 source당 1개다. Event 게시는 source당 한 번에 한 컨텍스트에서만 한다. payload는 inline으로만 담는다. 공유 SHM을 쓸 수 있는 프로세스는 신뢰 대상이다.

### 2.8 CBS 예산 관리와 Event/Job 관리의 관계

두 책임은 §2의 공통 정의를 따른다. 명시적 Event 연결은 Event/Job 관리 수단이며 앱의 하위 유형이 아니다(MOD-011).

- **연결 없이도 유지**: CBS 예산 관리, CPU 고정, BUDGET_EXCEED, BPF 실행 구간 기록.
- **연결 없이는 얻지 못하는 정보·감시**: Event 식별과 도달 시각, Job 기록, MIT 계수와 MIT_VIOLATION, Event 기준 DMISS. BPF 실행 구간에서 Event나 Job 마감을 추정하지 않는다.
- **추가 플래그 없음**: P1은 이 책임 구분을 위한 추가 분류·구성 플래그를 두지 않는다. source에 Event 기록이 없으면 DeadlineMonitor가 감시할 객체가 없는 것이며, 일시적인 게시 침묵이 앱을 재분류하지 않는다.
- **동일한 수용 판정**: TIMPANI-O는 모든 L2 태스크에 같은 수용식을 쓴다(CBS-004). Event 기록이 없을 때도 선언 D는 커널 활성화 기준의 수용 판정 파라미터로 남으며, 감시되는 Job 마감이 아니다.

## 3. 핵심 유스케이스 (Core Use Cases)

### UC-01: 정상 Event 수락 및 CBS 기반 실행 (P1)
1. L2 태스크의 워커가 명시적 연결 경로에서 Event를 기다리며 대기한다. 워커는 커널 수준에서 잠들어 있을 수 있다.
2. 입력 어댑터가 Event를 도달 시각과 함께 게시한다. 연결 경로가 수락하면 `(gen, seq)`와 `t_dl = t_arr + D`가 고정되고 Event가 감시 대상이 된다(R1).
3. 워커가 Event 하나를 취득하여 Job을 시작한다(`t_begin`). 예산은 보충 윈도우 단위로 부여되므로 Job 시작이 예산을 새로 주지는 않는다.
4. TIMPANI-N BPF 스케줄러는 해당 태스크의 CBS 잔여 예산(`remaining_us > 0`, 깨움 시 활성화 보충 규칙을 적용한 뒤)을 확인하고 배정 CPU의 L2 큐에 넣는다. 배정 CPU에서 L1 TT 슬롯이 실행 중이 아닐 때(Gap 구간) 실행되며 사용한 CPU 시간만큼 예산이 차감된다.
5. 워커가 처리를 마치고 명시적으로 완료를 게시하면 Job은 COMPLETED로 끝난다. `t_end ≤ t_dl`이면 마감 충족이다.
6. 워커가 다음 Event를 기다리러 가면 실행 구간이 커널에서 끝난다. 큐에 Event가 있으면 워커는 잠들지 않고 다음 Job을 시작한다(R3).

### UC-02: 예산 소진 후 추가 실행 제한 및 보충 (P1)
1. 예상보다 빈번한 Event 또는 긴 실행 시간으로 태스크의 CBS 잔여 예산(`remaining_us`)이 `0`에 도달한다(예산 소진). 소진만으로는 스로틀되지 않으며 2번 항목의 규칙을 따른다.
2. 정확히 소진하고 잠들면 스로틀하지 않는다. 계속 runnable이거나, 깨어날 때 활성화 보충 규칙을 적용한 뒤에도 잔여 예산이 0이면 추가 실행 전에 Throttled 큐로 옮긴다.
3. 현재 보충 윈도우(커널 활성화 시점부터 $T_s$)가 끝나면 예산이 $C_s$로 회복되고 새 윈도우가 시작되며, 태스크는 다시 L2 큐로 올라가 실행을 재개한다. 보충은 **다른 태스크의 활동 여부와 무관하게** 바운드된 지연 내에 이루어진다(PRT-003). 이 동안 마감이 지나면 PRT-009에 따라 실패가 감지된다.

### UC-03: TT + CBS 공존 하 L1 보호 (P1)
1. 동일 Isolated CPU에 L1(TT) 태스크 A(period 20 ms, WCET 2 ms)와 명시적 연결을 쓰는 L2(CBS) 태스크 X(MIT 18 ms, WCET 2 ms, D 5 ms)가 배치된다(예시 수치).
2. X에 Event가 A의 TT 슬롯 시작 0.5 ms 전에 도달한다. X는 Gap에서 실행을 시작하되 슬라이스가 "다음 TT 시작까지"로 제한되어 A 시작 전에 CPU를 양보한다.
3. A가 슬롯을 마치면 X가 재개되어 잔여 예산 내에서 완료한다. A의 활성화 지터는 X의 존재 여부와 무관하게 REQ-NFR-001 바운드 내에 있다.

### UC-04: 런타임 L2 워크로드 추가/제거 (P1 기본 / P2 무교란)
1. 시스템이 L1/L2 워크로드를 실행 중인 상태에서 Pullpiri가 새 L2 워크로드 Y를 `AddSchedInfo`로 등록한다.
2. TIMPANI-O는 Y의 수용 판정을 수행하고 성공 시 테이블을 발행한다(P1: 전체 테이블 재발행 허용. P2: 영향 노드만, epoch 유지).
3. TIMPANI-N은 Y를 추가한다(P1: 기존 태스크의 정상 재등록 허용. P2: 기존 L1/L2 활성화 무누락 보장). 제거(`RecoveryService` STOP) 시에도 동일하다. 제거 또는 재등록 시 열린 Event는 §2.3 규칙에 따라 닫힌다(IF-007).

### UC-05: 동일 CPU 다중 L2 서버 (P1)
1. 한 Isolated CPU에 L2 태스크 X(D 5 ms)와 Z(D 20 ms)가 배치되고, 두 Event가 거의 동시에 도달한다.
2. TIMPANI-N은 정의된 순서 정책(P1: 활성화 순서 FIFO)에 따라 디스패치하며, 수용 판정(CBS-004)은 그 정책 하에서 두 태스크 모두의 마감 충족을 사전에 확인한다.

### UC-06: MIT 위반 버스트 (P1)
1. 입력 측 오동작으로 X에 Event가 MIT보다 짧은 간격(예: MIT/3)으로 반복 도달한다.
2. 연결 경로는 **도달 기준**으로 MIT 위반을 계수하고, 위반된 Event도 수락하여 큐에 넣는다. X는 CBS 예산 범위 내에서만 실행되어 L1 및 타 L2에 영향을 주지 않는다. X가 처리 중일 때 도달한 Event는 `QUEUED`로 남아 다음 Job이 소비한다(R2~R4). 유실은 없으며, 큐 깊이의 증가와 MIT 위반 계수로 관측된다.
3. 스로틀 중에 마감이 지난 Job의 실패는 감지 경로에서 `THROTTLED` 표식을 받고, 같은 source의 MIT 위반이 시간상 가까우면 `MIT_RELATED` 표식을 받는다(PRT-007). 표식은 원인 판정이 아니다. 원인 분류와 원인별 복구는 P2다(DDR-008 D-23).

### UC-07: 이벤트 침묵 감시 (P2, 참고)
기대 최대 도달 간격 내에 Event가 도달하지 않으면 `WATCHDOG` 폴트를 발생시킨다.

### UC-08: 대기·스로틀 중 마감 경과 감지 (P1)
1. 워커가 이전 Job을 끝내지 못해 Event E가 `QUEUED` 상태에 있거나, E의 Job이 CBS 예산 소진으로 스로틀된다.
2. `t_dl`이 지나도 E는 열려 있다. DeadlineMonitor가 워커의 완료를 기다리지 않고 MISSED를 설정하고(PRT-009, 감지 지연 TIM-009), 실패 기록을 TIMPANI-O 보고 경로로 넘긴다(TIM-010).
3. 이후 워커가 E를 처리해 완료하더라도 같은 Job의 실패는 중복 계수되지 않는다. 완료 기록은 별도로 남는다.

(d) QUEUED 또는 스로틀 중에 지난 마감이 TIM-009의 합의된 상한 안에 감지된다. 전 구간에서 그 CPU의 TT_START/TT_END 이벤트는 0건이다. | 범용 이벤트 생성기 + BPF 트레이스 + Job 기록 | CBS-007, CBS-004, PRT-003, PRT-009 | P1 |
| **AC-008-18** | TT 최초 추가·마지막 TT 제거 시 유지 L2 보존 | L2 엔트리는 그대로 두고 그 CPU의 첫 TT 태스크를 추가하거나 마지막 TT 태스크를 제거하는 테이블 갱신(갱신 뒤 테이블이 수용 판정을 통과하는 경우)을 10회 반복하는 동안: 유지되는 L2의 잔여 예산과 보충 윈도우가 초기화되지 않고, 열린 Event의 `(gen, seq)`와 $t_{dl}$이 바뀌지 않으며, 갱신 때문에 생긴 CANCELLED·ABANDONED가 0건이고, 데몬 재시작이 없다. | **AC-008-19** | 잘못된 cpuset 배치의 명시적 실패 | 허용 CPU 집합에 배정 CPU가 없는 워커에 대해: 바인딩을 시도한 시점에 명시적 오류가 기록되고, 그 태스크는 SCHED_EXT로 전환되지 않으며, BPF 스케줄러가 계속 동작하고, 같은 노드의 다른 L1/L2는 영향을 받지 않는다(L1 DMISS 0). cpuset을 바로잡은 시각부터 지연 식별 상한(TIM-006, T_bind) 안에 바인딩된다. 이 경우 측정 시작점은 스레드 생성 시각이 아니라 cpuset 정정 시각이다. | 잘못된 cpuset을 일부러 준 통합 테스트 | CBS-008, CBS-005, DET-006 | P1 |

## 12. 선행 샘플 앱(PR #50~#52)과의 관계 및 가이드 방향

### 12.1 현황
- [eclipse-timpani/timpani26#50](https://github.com/eclipse-timpani/timpani26/pull/50) (FCW L1/L2 예제 + 이상 주입), [#51](https://github.com/eclipse-timpani/timpani26/pull/51) (timpani-n 스레드 이름 식별), [#52](https://github.com/eclipse-timpani/timpani26/pull/52) (예산 초과 주입, 프레임 로그)는 **저장소에 존재하지 않는 과거 DDR-008 검토 초안**("DDR-008 §2.3", "DDR-008 LLD §1.3", "FR-041")을 근거로 작성되었다.
- 그 초안은 SOME/IP를 코어 계약에 직접 언급했고, 그 결과 `libtimpani_rt`가 service/instance/event ID를 인자로 받는 API, 자체 SHM(`/timpani_rt`), 라이브러리 측 MIT·E2E 폴트 판정(3 ms 하드코딩)을 갖게 되었다. TIMPANI-N은 이들을 소비하지 않으므로 현재 "라이브러리 로그"에 머문다.
- PR #51의 스레드 이름 식별은 본 요구사항(DET-006 P1의 전제)과 부합하며 유지한다.

### 12.2 가이드 방향 (상세는 HLD-008 §8, LLD-008 §7)
Phase 1 설계는 FCW 한 가지가 아니라 여러 종류의 Event를 같은 방법으로 다룰 수 있어야 한다. 그래서 가이드는 두 층으로 제공한다. (a) 임의의 Event 종류를 공통 모델에 올리는 **적용 방법론**(HLD-008 §8.1 계약, §8.2 절차, §8.3 Event 종류별 적용표). (b) 그 방법론을 FCW 예제에 적용한 **파일별 수정 가이드**와 실행별 기대 관측(HLD-008 §8.4, 코드 스케치는 LLD-008 §7.2). 아래 표는 (b)의 방향을 요약한 것이다.

| 항목 | 현행(PR #50/52) | 가이드 방향 (P1) |
|:--|:--|:--|
| 이벤트 등록 | `timpani_evt_register(wl, task, svc, inst, evt, mit)` | 제거. TIMPANI는 Pullpiri `SchedInfo`(MIT 필드)로만 L2를 안다. 미들웨어 구독은 앱이 처리 |
| 도달 표시 | `timpani_evt_mark_arrival(svc, inst, evt, seq)` → 자체 SHM | 명시적 연결 경로의 **게시**(DET-004(a), IF-005): 수신 스레드(vsomeip 콜백)에서 도달 시각과 payload를 넘긴다. 거절되면 사유를 확인하고 해당 Event를 만들지 않은 것으로 처리한다(계수는 연결 경로가 한다). 핸들은 초기화 때 source 핸들 획득(DET-004(d))으로 얻는다. 생산자 스레드는 기준 생산자 구성(A-10)을 따르고, 대상 구성에서 $L_{post}$가 TIM-011 상한 이내인지 측정으로 확인한다. |
| 워커 대기 | `std::condition_variable` 대기 | 명시적 연결 경로의 **Event 대기(wait)**(DET-004(b))에서 Job 시작을 확정·기록하고 Event 한 건을 인계받으며, 처리 후 **명시적 종료**(DET-004(c))로 완료 또는 폐기를 게시한다. 앱 자체 큐는 두지 않는다. 명시적 Event 연결 없이 표준 블로킹 대기를 유지해도 CBS 예산 관리는 유지되지만 Event 기준 마감은 감시하지 못한다 |
| CBS bind/unbind | `timpani_cbs_bind_thread/unbind` (스케줄링 효과 없음) | 제거. Job 경계는 wait 내부의 Job 시작과 명시적 종료로, 도달은 게시로 정해진다 |
| MIT·E2E 판정 | 라이브러리 내부(3 ms 하드코딩) | 제거. TIMPANI-N이 `MIT_VIOLATION`/`DMISS`를 판정·보고(PRT-004/005/009). 앱은 자체 로그만 유지 가능 |
| 서버 키 해시 | `FNV("wl:task")` | 앱에서 해시 불필요(제거) |
| 워크로드 등록 | `mock_pullpiri.yaml` SPORADIC, `period`=MIT | MIT 전용 필드 사용(IF-001). 전환 기간 `period` 허용 |
| 이상 주입 옵션 | `--burst-ms`, `--overrun-ms`, `-be`, `--wakeup-delay-ms`, `--tt-overrun-ms` | 유지. AC-008-03/04/07/14를 FCW에서 재현하는 수단(기준 검증 수단은 범용 이벤트 생성기). 단 `--wakeup-delay-ms`의 지연은 워커 안이 아니라 수신 측(게시 전)으로 옮긴다. 워커 안의 수면은 Job 내 블로킹이며 수용 판정의 보장 밖이다(A-06) |
| 앱 큐·로그 | 워커와 수신 스레드가 같은 뮤텍스를 잡는 큐, Job 안에서 `std::cout` | 공통 Event 큐가 payload를 보관하므로 앱 자체 큐는 두지 않는다. 워커의 프레임별 콘솔 출력은 제거한다. 로그 링은 두지 않으며, 프레임과 Job의 대응은 Job 기록(OBS-002)으로 얻는다 |
| 검증 | 앱 stdout 로그 | TIMPANI-N의 Job 기록과 실행 구간 기록(OBS-002) 기준으로 판정. 앱 로그는 보조 |
| 스레드 배치와 정책 | FCW 예제는 affinity나 정책을 정하지 않음. 컨테이너 cpuset에 따름 | 등록 워커는 앱이 정책·affinity를 스스로 정하지 않고 `SCHED_EXT`/BPF CBS를 따른다. 비워커 정책 선택·관리는 P1 범위 밖이다. cgroup·cpuset 배치는 시스템 책임이며 워커만 격리하는 목표는 검토 중이다(A-09). 배정 CPU가 허용 집합에 없으면 바인딩이 명시적으로 실패한다(CBS-008, AC-008-19) |

### 12.3 역할 분담 원칙
- **TIMPANI 저장소**: 요구사항·설계 확정 → `timpani-o`/`timpani-n`/`libttsched` 구현 → Event 종류 적용 방법론과 샘플 앱 변경 가이드 발행(HLD-008 §8).
- **샘플 앱(FCW)**: 가이드에 따라 어댑터(vsomeip ↔ 명시적 Event 연결 API)로 축소. SOME/IP 고유 코드는 `examples/someip` 안에만 존재.
- 두 작업은 **설계 확정 이후** 병행하되, 인터페이스(연결 API 시그니처, proto 필드, Event 큐 상수)는 LLD-008 확정본을 단일 기준으로 삼는다. 이 세 항목은 Project Leader 승인 후에만 확정된다(OI-19).
